# Playwright Test Case Design

## Scope and traceability

The current Playwright discovery reports **76 tests in 8 spec files** (`npm run test:list`), not 96. This sheet transcribes those discovered tests; it does not claim coverage for scenarios that are not in the code.

The Submission 1 risk register was not included in the files available for this revision. The risk links below are therefore provisional risk themes, not invented Submission 1 IDs. Replace each `S1-TBD` with the matching risk ID and confirm or revise the mapping against the submitted risk register before final hand-in.

Seeded-defect candidates were checked against the lab's `SeededDefectSeeder` and defect documentation. A candidate is included only when the automated assertion directly exercises that defect behavior. Other tests state that no matching candidate was confirmed; they remain valuable functional tests. Candidate mapping is not evidence that a defect is active or was observed.

Severity reflects potential impact if the behavior is defective: **Critical** (unauthorized access or invalid submission), **High** (eligibility, financial, or legal/data-integrity failure), **Medium** (module behavior/validation failure), **Low** (minor usability or presentation issue). Priority is execution order: **P1** core access, important business rules, and submission barriers; **P2** standard functional coverage; **P3** conditional or lower-impact edge cases.

Precondition abbreviations: **APP** = application available at `APP_BASE_URL`; **AGENT** = valid, dedicated lab agent credentials; **DRAFT** = a new draft owned by that agent; **API** = `/api/health` is available; **KEY** = valid API key. Any credentials, lockout accounts, submitted applications, or pre-seeded records are supplied through the documented environment variables, never hard-coded.

## Execution and evidence notes

- `npm run test:list` currently discovers 76 scenarios. The review comment's count of 96 does not match this checkout and should be reconciled with the submitted source/version.
- API scenarios first check `/api/health`; a 404 marks them skipped because the API route file is not registered. Other unexpected health failures fail the test setup.
- Several scenarios are intentionally gated by dedicated credentials, an API key, disposable accounts, or seeded records. Report pass/fail/skip counts and reasons; do not describe skipped tests as passed.
- Before final submission, replace the provisional `S1-TBD` themes using the actual Submission 1 risk IDs. Check active seeded defects with the mentor; a candidate mapping alone does not establish that the candidate is enabled.
- After running on the assigned VM, attach that run's HTML report and record its URL, date, exact command, counts, and each failure's classification (application, automation, data, or environment). A local report is not VM execution evidence.
